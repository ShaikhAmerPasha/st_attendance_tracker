## Round 3: real 403 on attaching a file at checkout

User hit `POST /api/method/upload_file` → 403 in the browser attaching a file to an existing task on the checkout page. Root-caused (not guessed) via live reproduction against the real failing user/record:

Frappe's generic `upload_file` endpoint checks write permission by calling `frappe.get_doc("Task Entry", name).check_permission("write")`. For a child (`istable`) doctype, that's supposed to delegate to the parent (`has_child_permission` in `frappe/permissions.py`) — which is exactly the mechanism I'd verified before making the original `Daily Task` → `Task Entry` rename. What I hadn't verified: `has_child_permission`'s delegation reads `getattr(child_doc, "parent_doc", child_doc.parent)` to find the parent doc — but `parent_doc` is a `@property` defined on *every* `BaseDocument` (`base_document.py`), so it always "exists" (returning `None` on a standalone-loaded child) and `getattr` never falls through to the intended `.parent` name string. The recursive permission check on the parent `Daily Work Log` then runs with `doc=None`, so `is_owner` can never resolve `True` — an if_owner-gated permission (ours, matching the old `Daily Task` doctype's own permission row) is unconditionally denied. This is a genuine core-Frappe limitation for if_owner-restricted child doctypes reached this way, not fixable via DocType permission config. Confirmed empirically with `frappe.permissions.has_permission(..., debug=True)` showing `if_owner: {"write": 0}` for the exact failing user/task, then confirmed the *other* rename (`frappe.client.set_value`, used for inline description/remarks edits) is unaffected — it resolves the full parent document explicitly before calling `.save()`, never hitting this code path.

**Fix:** added a dedicated `upload_task_attachment` whitelisted endpoint in `api.py` that does the same `_assert_task_owner` check already used elsewhere, then saves the `File` doc directly with `ignore_permissions=True` (replicating exactly what core `upload_file` does after its permission check passes). Updated `daily_checkin.html`'s `uploadTaskFiles()` to route existing-task uploads through this endpoint instead of core `upload_file`; a brand-new (not-yet-saved) task still uses core `upload_file` as an orphan upload (no doctype/docname), unaffected since that path never hits `check_write_permission`'s doctype branch. Added two regression tests: ownership denial (fires before the file is ever touched) and a successful upload (using a minimal fake-request stub since `frappe.request` isn't populated in the test harness). Re-verified against the exact real user/task that originally 403'd — succeeds now.

## Round 4: slow checkout with large attachments

User reported checkout taking a long time to submit when attaching images/zip/PDF files, with the button stuck on "Submitting..." before eventually completing. This is exactly spec Section 8.3's flagged-but-deferred item ("move notification emails fully off the request path") — now actually hit in practice.

**Root cause:** `frappe.sendmail(..., now=False)` doesn't send over SMTP synchronously, but it still has to base64-encode every attachment and write a full Email Queue record *inside the request* before returning — and `submit_eod_log` was doing this twice in a row (HR/Team-Leader email, then the employee's own confirmation email), both carrying the same attachments, entirely inside the synchronous checkout HTTP request.

**Fix:** extracted the notification-building logic for both check-in and checkout into two standalone functions, `_send_checkin_notifications`/`_send_eod_notifications` (each re-fetches the employee + `Daily Work Log` fresh by name/date rather than closing over already-built objects, since a background job runs in a separate process). `submit_morning_log`/`submit_eod_log` now hand these to `frappe.enqueue(..., queue="short", enqueue_after_commit=True)` instead of calling them inline — `enqueue_after_commit` guarantees the worker never reads the just-saved `Daily Work Log` before this request's transaction is durably committed. The checkout HTTP response now returns as soon as the attendance data is saved; the emails go out moments later from a background worker.

Verified this isn't just a paper fix: this dev bench actually has a `bench worker` process running, so re-ran the exact enqueue call live and watched `logs/worker.log` — the job (`st_attendance_tracker.api._send_eod_notifications`) is picked up and logged "Job OK" within milliseconds of the checkout request returning. The enqueue call itself took ~0.002s regardless of attachment size, versus the previous inline path that scaled with attachment size.

Because `bench run-tests` has no worker draining the queue, every test that calls `submit_morning_log`/`submit_eod_log` stopped incidentally covering the email-building code (it just enqueues now — plausible, hadn't hit this before touching notifications). Added two direct tests (`test_9_1`, `test_9_2`) that call `_send_checkin_notifications`/`_send_eod_notifications` synchronously — the same functions the enqueue call points at — including one with a real task attachment, closing that gap. Test suite now 73 tests.

## Round 4b: follow-up debug — where does the remaining time actually go

User asked to keep digging into *why* attachment emails are slow, beyond "it's now backgrounded." Measured for real (8MB test file, 3 HR/Team-Leader recipients) rather than guessing further:

- **`frappe.sendmail(now=False)` call itself: ~0.4s per call**, per attached 8MB file. This is what used to block the checkout request directly — `submit_eod_log` calls it twice (HR/TL email + employee email), so ~0.8s per attached file was added straight to the synchronous request before the Round 4 fix. Now fully backgrounded.
- **`EmailQueue.build_message()`, which runs later in the scheduled `frappe.email.queue.flush` job: ~0.35s per recipient**, and confirmed via source (`EmailQueue.attachments_list` re-parses its stored JSON fresh on every property access, so nothing persists across calls) that the attachment is genuinely re-read from disk and re-base64-encoded once per recipient, not cached. With 3 HR/TL recipients + 1 employee recipient, that's **4 full re-encodes of the same file** for one checkout. This is inherent to Frappe core's Email Queue design, not a bug in this app's code.

So with several attachments across images/zip/pdf, the real background cost genuinely stacks into several seconds — none of it blocking the user anymore, but real server work. The concrete fix identified (drop raw attachments from the multi-recipient HR/Team-Leader email, keep them only on the employee's own single-recipient confirmation email, since HR/TL can already view/download via the app's `get_task_attachments`/`view_task_attachment`) would remove the recipient-count multiplier — **user chose to keep attachments on all emails as-is**, so no code change made here. Documented for future reference if this becomes a real bottleneck at higher checkout volume.

## Round 5: Redis caching for ST Attendance Settings

User asked (with an already fully-specified implementation) to cache the `ST Attendance Settings` singleton the same way `_get_team_members()` caches team lookups — read on nearly every check-in/checkout/dashboard load, changes a handful of times a year.

Added `_get_attendance_settings()` (api.py, next to `_get_team_members()`) and `clear_attendance_settings_cache()`, wired to `ST Attendance Settings`'s `on_update` in `hooks.py`. Replaced the direct `frappe.db.get_single_value("ST Attendance Settings", ...)` reads in `api.py` (`_get_hybrid_office_days`, `get_management_dashboard`) and `daily_work_log.py` (`_check_late`) — plus one the task didn't name: `www/daily_checkin.py` has its own literal duplicate of `_get_hybrid_office_days()` (not importing api.py's), which also read the setting directly on every `/daily-checkin` page load. Pointed it at the same cached helper rather than leaving a second uncached copy of the exact same read.

**Deliberately left uncached — two call sites, both for correctness reasons, not oversights:**
- `st_attendance_tracker/st_attendance_tracker/doctype/daily_task_log/daily_task_log.py` — the legacy (pre-refactor) `Daily Task Log` controller, frozen and unused by the live app during the Round 1 verification window. Out of the stated scope (`api.py` and `daily_work_log.py`) and not worth touching code that's slated for removal.
- `st_attendance_tracker/tasks.py`'s `_already_sent_today()` — this reads/writes scheduler "last sent" marker fields on the *same* Settings singleton, under an explicit `for update` row lock, in the same transaction, specifically to dedupe concurrent scheduler fires. It writes via `frappe.db.set_single_value()` (a raw DB write that never triggers `on_update`, so the cache would never invalidate) and needs the just-written value visible on the *next* read within the same request. Caching this field would silently break the dedup guard it exists for — not the same "changes a few times a year" category the caching rationale describes.

**Found and fixed a real bug while writing the required "cache hit doesn't re-hit the DB" test** — not something I'd have caught without writing that test, and not something visible from the reference `_get_team_members()` implementation either, since nothing exercises that code path against it: `RedisWrapper.get_value()` (Frappe core), called without `expires=True`, writes a *negative* cache entry (`None`) into `frappe.local`'s per-request memory cache on a miss — and `set_value()` with a TTL never clears that local entry afterward. So the very next `get_value()` call in the same request/process would keep returning the stale local `None` without ever checking Redis again, even though Redis now holds the real value just written. Fixed by passing `expires=True` to the read in `_get_attendance_settings()`. Left `_get_team_members()` completely untouched per the explicit scope — it likely has the identical latent issue, but that's a separate, pre-existing thing for the user to decide on, not part of this task.

Added 3 tests (`test_10_1`–`test_10_3`): cache-miss returns the correct live value, a cache-hit genuinely skips the DB (proven by making `frappe.get_single` fail if called), and saving the settings invalidates the cache so the very next read reflects the new value. All three mutate the real shared `ST Attendance Settings` singleton and restore the original value in a `finally` block. Full suite: 76/76 passing. Final grep confirms zero remaining `get_single_value("ST Attendance Settings", ...)` calls anywhere except the two deliberately-excluded ones above.

## Bugs found and fixed during implementation (via hands-on testing on the excel dev site)

1. **Frappe auto-defaults every `Time`-fieldtype field to `nowtime()` — twice.** Once in `frappe.new_doc()`, and again on *every* `insert()` via `Document._set_defaults() -> update_if_missing()`, which treats a field as "missing" using `is None` (not falsy) and re-pulls a fresh `nowtime()` from a throwaway new-doc template. Harmless on the old two-doc model (a Morning Check-In log's unused logout/lunch fields were never read), fatal here since all four time fields now live on one doc — a same-day check-in with no checkout yet would silently inherit a garbage logout_time/lunch window and fail lunch-duration validation. Fixed centrally in `DailyWorkLog.__init__` using the documented `dont_update_if_missing` escape hatch (`base_document.py`), rather than scattering the fix across every call site. Found ~186/59 already-migrated dev-site records with this corruption; wiped and re-ran the migration after the fix.
2. **Rollover re-saving an already-locked source document.** `_rollover_pending_tasks`/`_safety_rollover` need to flip status fields (Done/Rolled Over) on the *source* day's `Task Entry` rows — but that source Daily Work Log is often the just-eod_submitted doc itself, and routing the status change through `work_log.save()` re-triggered the parent's own `_check_locked()` guard, blocking EOD submission whenever any task actually rolled over. Fixed by writing the source-row status directly via `frappe.db.set_value("Task Entry", ...)` (bypassing the parent's validate(), same pattern the old standalone-`Daily Task` code used for this exact "internal housekeeping, not a user edit" case) — the target (next day's) log still goes through the normal ORM append+save path.
3. **Dropped a real business rule while merging the two log doctypes.** The old `Daily Task Log.validate()` required `login_time` to be resolvable before allowing an "End of Day" save, throwing "Morning Check-In is required before submitting End of Day." I didn't carry this over — caught by the ported `test_1_3_eod_without_checkin_blocked` test. Re-added to `DailyWorkLog.validate()`.

All three were caught by actually running `bench migrate` + `bench run-tests` against the real dev site, not by reasoning alone — this is why the test suite (step 7) and hands-on migration run (step 8) mattered before calling this done.
